# 搭子推荐系统 · 整体设计

> 状态：设计稿 v1（2026-11-14）
> 本文是整个推荐系统的总体设计与路线图。每个阶段的具体需求、设计与任务拆分放在 `openspec/changes/` 下，按阶段逐个落地。

---

## 1. 产品定位

一个**以兴趣为底座的垂直找搭子平台**，首发城市新加坡，面向华人年轻人（留学生 + 工作党）。

- 形态类似小红书的发帖：用户发「搭子帖」——我想去做某件事，缺人一起。
- 与小红书的区别：垂直、结构化，并且由平台**主动帮帖子找到合适的人**，不靠运气被刷到。
- 覆盖的兴趣：旅行、运动、桌游、学习、吃喝、文艺、夜生活等。
- 核心价值是「想做的事，找到人一起去做」。成为长期朋友是附带的结果，不是主要目标。

先做推荐系统本身（库 + 离线评估），再封装成 API，最后接 App。

---

## 2. 目标与指标

### 2.1 漏斗

```
发帖 → 被合适的人看到 → 有人申请 → 发帖人同意 → 真的成行 → 双方好评
                                                   ↑ 北极星：成行率
```

| 层级 | 指标 | 说明 |
|---|---|---|
| 北极星 | **成行率** | 发出的帖子中，凑齐人并实际成行的比例 |
| 体验 | 成行后互评好评率、放鸽子率 | 质量护栏 |
| 效率 | 帖子从发出到凑齐人的时间 | 垂直平台相对小红书的核心优势 |
| 推荐 | 曝光→申请转化、申请→同意转化 | 排序模型的直接目标 |
| 长期（次要） | 再约率、留存 | 交朋友的副产品 |

### 2.2 排序目标

```
score(user, post) = P(申请 | 曝光) × P(被同意 | 申请) × P(成行且好评 | 被同意)
```

中间一项说明这是**双向推荐**：推荐给我的帖子，发帖人也要愿意带我去。

### 2.3 约束

安全（硬过滤优先）、兴趣多样性、新帖与新发帖人有曝光机会、快到日期还缺人的帖子优先、快满员的帖子不过度曝光。

## 3. 与普通推荐系统的关键差异

| 特点 | 带来的问题 | 设计应对 |
|---|---|---|
| 帖子是一次性的、生命周期短 | 每个帖子都是冷启动物品，基于物品 ID 的协同过滤失效 | 用**属性**表示帖子：兴趣标签、时间、地点、要求、发帖人 |
| 双向选择 | 我想去 ≠ 对方愿意带我 | 建模 P(申请) × P(被同意)，并做双向硬过滤 |
| 时间、地点、人数是硬约束 | 时间对不上、已满员的帖子推了也没用 | L1 硬过滤 |
| 活动类型差异大 | 旅行与看展的匹配严格程度完全不同 | 按类型使用不同的特征和权重（旅行需要额外问卷） |
| 反馈稀疏且慢 | 一个人一个月可能只成行几次 | 使用多级信号（浏览、收藏、申请、成行、互评）；开发期用模拟器 |

## 4. 推荐任务

| 优先级 | 任务 | 输入 → 输出 |
|---|---|---|
| **P0** | 帖子信息流推荐 | user → 排好序的帖子列表 |
| **P0** | 帖找人（主动邀约） | post → 最可能申请且符合要求的 N 个用户 |
| P1 | 搜索排序 | user + query → 帖子列表 |
| P1 | 想去清单匹配 | wish → 匹配的帖子 / 匹配的其他 wish（「你们可以一起发起」） |
| P2 | 老搭子推荐 | user → 一起成行过、互评好的人的新帖 |

## 5. 兴趣体系（底座）

- **三层标签树**：大类 → 子类 → 具体（如 `旅行 > 东南亚 > 清迈`、`运动 > 羽毛球`），叶子节点可以带属性（水平、风格）。
- **相近兴趣关系**：如 飞盘 ~ 腰旗橄榄球、剧本杀 ~ 密室，带权重，用于召回扩展和冷启动。
- **匹配层级**：同一叶子 > 同子类 > 相近兴趣 > 同大类。
- **文本理解（V2）**：帖子描述是中英混杂的自由文本。使用多语言文本向量把描述映射到标签，并支持语义搜索。

## 6. 数据模型

### 6.1 用户（User）
- 基本信息：年龄段、性别（可选）、身份（学生 / 工作）、常住区域或最近的地铁站、语言
- 兴趣：标签 + 水平
- 可用时间：每周时段网格（工作日晚、周末白天、周末晚……）
- 风格：I/E、喜欢小局还是大局、节奏（特种兵 / 躺平）、作息
- 预算区间、可接受的通勤时间
- 偏好与限制：只接受同性别、年龄段等
- 派生：信用分（到场率）、各兴趣的偏好度（时间衰减）、活跃度、发帖人回复率与成行率

### 6.2 搭子帖（Post）
- 兴趣标签（叶子节点 + 属性）
- 时间：固定日期，或弹性窗口（如「12 月中任意 5 天」）
- 地点：本地为地铁站或区域坐标；旅行为目的地 + 出发地
- 人数：总人数、还缺几人
- 对搭子的要求：性别、水平、预算、风格（分硬性和软性）
- 费用方式、是否室外、语言
- 描述文本、图片
- 状态：招募中 → 已满 → 已成行 → 已结束 / 已取消

### 6.3 想去清单（Wish）
用户登记的意向，结构与帖子相同但没有发起人承诺。用于主动推送和清单之间的匹配。

### 6.4 行为日志（Interaction）—— 最有价值的数据

| 事件 | 用途 |
|---|---|
| **曝光**（位置、来源） | 必须记录，没有它无法训练、无法评估 |
| 浏览时长、收藏、私信 | 兴趣信号 |
| 申请（附留言） | P(申请) 的标签 |
| 发帖人同意 / 拒绝（以及响应时长） | P(被同意) 的标签 |
| 成行确认、到场、放鸽子 | 成行标签、信用分 |
| 双方互评 | 体验标签 |
| 举报、拉黑 | 安全过滤 |

### 6.5 关系图（辅助）
一起成行的次数、互评、共同搭子。用于老搭子推荐和信任背书，不作为核心特征。

### 6.6 隐私
遵守新加坡 PDPA：敏感字段可选，只采集需要的数据，取得用户同意。

## 7. 系统分层

```
请求(user, 时间, 位置)
  │
  ▼
L1 硬过滤   过期 / 满员 / 时间不重叠 / 不满足发帖人硬性要求 /
           不满足我的硬性偏好 / 拉黑 / 已申请 / 安全
  │
  ▼
L2 召回     兴趣树召回(同标签 + 相近) · 时间重叠召回 · 想去清单召回 ·
           文本相似召回(V2) · 新帖 / 探索召回
           （早期帖子量少，可以对全部候选打分，但保留召回接口）
  │
  ▼
L3 排序     预测 P(申请) × P(被同意) × P(成行好评)
           V1 规则加权 → V2 逻辑回归 / LightGBM → V3 多任务
  │
  ▼
L4 重排     多样性 · 紧迫度（快到日期还缺人）· 快满员降权 ·
           新发帖人保底曝光 · 探索
  │
  ▼
L5 解释     「你也想去清迈 · 时间重叠 4 天 · 预算接近 · 发帖人 3 次成行均为好评」
  │
  ▼
返回 Top-K，并记录曝光日志 ──▶ L0 数据层（日志 → 特征 → 训练 → 评估 → 上线）
```

### 7.1 排序特征

| 类别 | 特征 |
|---|---|
| 用户 × 帖子 | 兴趣匹配层级、时间重叠比例、通勤时间 / 距离、预算差、水平差、风格相似度 |
| 双向 | 我满足对方要求的程度、对方满足我偏好的程度 |
| 帖子 | 缺人数 / 满员率、距离活动开始的时间、新鲜度、是否室外 |
| 发帖人 | 回复率、同意率、历史成行率、互评分 |
| 用户 | 信用分、活跃度、各兴趣偏好度 |
| 社交（辅助） | 共同搭子数、是否老搭子 |

### 7.2 帖找人通道
输入一个帖子，在所有用户中使用同一套特征反向打分，并加上频控（每人每天最多收到 N 条邀约推送）。

### 7.3 冷启动

| 情况 | 策略 |
|---|---|
| 平台没有数据 | **模拟器**：生成带有「隐藏真实偏好」的虚拟用户和行为，可用于评估算法 |
| 新用户 | 注册问卷 → 基于内容的推荐 + 探索 |
| 新帖子 | 属性 + 发帖人历史 |
| 新发帖人 | 重排层保底曝光 |

## 8. 评估

- **离线**：按时间切分训练和测试集；Recall@K、NDCG@K、覆盖率、多样性。基于模拟器计算**模拟成行率**（推荐结果在模拟世界里能促成多少成行）。
- **在线（上线后）**：A/B 测试，关注申请转化、同意转化、成行率、好评率。
- 每个版本的模型都要和上一版及简单基线（热门、随机）对比。

## 9. 技术栈与工程结构

- Python 3.12、numpy、pandas、scikit-learn、LightGBM
- API：FastAPI；存储：起步用 SQLite，之后换 Postgres
- 推荐逻辑是独立的 Python 库；API 只是薄薄一层包装

```
dazi/                 推荐系统库
  taxonomy/           兴趣标签树
  schema/             数据模型
  sim/                模拟器
  recall/ rank/ rerank/ explain/
  eval/               离线评估
api/                  FastAPI（Phase 5）
docs/                 设计文档
openspec/             需求 / 变更规格
```

## 10. 路线图

每个阶段对应一个 OpenSpec change：

| 阶段 | OpenSpec change | 内容 |
|---|---|---|
| **Phase 1** | `add-recsys-foundation` | 兴趣标签树、数据模型、模拟器 |
| Phase 2 | `add-feed-ranking-v1` | 信息流 V1：硬过滤 + 规则打分 + 解释 + 离线评估框架 |
| Phase 3 | `add-ml-ranking` | 机器学习排序、双向打分 |
| Phase 4 | `add-post-invite-and-wish-matching` | 帖找人、想去清单匹配 |
| Phase 5 | `add-recsys-api` | FastAPI：`/feed`、`/posts/{id}/invite-candidates`、`/wishes/matches`、`/search`、`/interactions` |
| Phase 6 | （可选） | 文本向量语义搜索、在线探索（bandit）、多任务模型 |
